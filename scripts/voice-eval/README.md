# 音声検索の評価

文字起こし(`/api/transcribe`)と、その結果での商品検索(`/api/search`)をまとめて測る。
**音声認識まわりを変えたときは、必ずここで前後を比較してから採用すること。**

## 使い方

開発サーバー(`npm run dev`)を起動した状態で:

```bash
cd scripts/voice-eval
node make_fixtures.mjs   # 評価用音声を作る(macOSのみ・初回だけ)
node add_noise.mjs       # 雑音入りを作る(初回だけ)

node eval.mjs clean
node eval.mjs snr20
node eval.mjs snr10
node eval.mjs snr5
```

`audio/` は生成物なのでコミットしない。macOS以外で評価したいときは、
誰かが生成した `audio/` をそのまま渡せば `eval.mjs` は動く。

## 見方

`商品到達 31/45` が主な指標で、文字誤り率は補助。
「唐揚げ」を「から揚げ」と書いても検索は通るため、文字誤り率だけ追うと
実害のない誤りに引きずられる。

**4条件すべてで測ること。** 雑音耐性を上げる変更は静かな環境で退行させやすく、
片方だけ見ていると気づけない。

## これまでの計測

雑音を固定した(乱数に種を与えた)あとの実測値。

| 条件 | turbo(旧) | whisper-ja-760M(現行) |
|---|---|---|
| clean | 43/45 (7.9%) | **44/45 (5.3%)** |
| snr20 | 41/45 (11.2%) | **42/45 (8.2%)** |
| snr10 | 36/45 (88.2%) | **39/45 (18.0%)** |
| snr5 | 28/45 (37.5%) | **31/45 (30.7%)** |

turboのsnr10で文字誤り率が88.2%と跳ねているのは、暴走した繰り返し出力
(「〜引き 引き 引き…」の類)が数件混ざるため。条件をまたいで比べられる数字ではないので、
判断は商品到達で行うこと。現行モデルではこの暴走が出ていない。

試して**効かなかった**もの(同じことを繰り返さないための記録):

| 試したこと | snr10の文字誤り率 | 判定 |
|---|---|---|
| 前処理(80Hz高域通過・音量正規化・無音除去) | 23.3% → 26.1% | 悪化。Whisperが内部で正規化しているため逆効果 |
| ビームサーチ `num_beams=5` | 23.3% → 23.3% | 変化なし。1件2.0秒→5.4秒と遅くなるだけ |
| 語彙プロンプト(商品名を`<\|startofprev\|>`で提示) | 23.3% → 225.6% | 破綻。下記のとおり実装側が未対応 |

モデルの差し替えだけが効いた。`efwkjn/whisper-ja-760M` は turbo を日本語45000時間
(雑音増強込み)で追加学習したもので、構造が同じなので `MODEL_ID` を変えるだけで入れ替わる。

語彙プロンプトについて補足。`@huggingface/transformers` 4.2.0 は Whisper の `prompt_ids` を
**実装していない**(`WhisperGenerationConfig` に型はあるが、`generate()` 側では
`// prompt_ids = null,` とコメントアウトされている)。`decoder_input_ids` に
`<|startofprev|>` から自前で組み立てて渡してみたが、29トークンの短い文脈文でも
同じように壊れ(246.6%)、プロンプト文そのものが出力に漏れた。
長さの問題ではないので、この構成では語彙プロンプトは使えない。

雑音下で崩れているのは探索・前処理・プロンプトではなく音響モデル側なので、
次の手は学習になる。`notebooks/whisper_japanese_finetune.ipynb` を参照。

## 雑音について

実店舗の録音が用意できないので合成している(空調の低い唸り + ざわめき + ときどきの物音)。
`add_noise.mjs` の `storeNoise` と、Colabノートブックの `store_noise` は同じ作り方にしてある。
**片方だけ変えないこと。** 学習と評価で雑音の質が食い違うと、
良くなったように見えて実際は効いていない、という測り方になる。
