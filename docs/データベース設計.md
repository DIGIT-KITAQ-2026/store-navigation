# store-navigation データベース設計 (Supabase)

## 1. 設計方針・背景

Unity座標を「棚バーコード(物理的な棚)」とは別に『位置/座標管理データ(`shelf_locations`)』として独立させて紐付ける構成にしている。

- **レイアウト変更への柔軟性**: 棚(物理的な什器)とマップ上の座標(Unity内の位置データ)が分離されているため、店舗のレイアウト変更や棚の移動に対して柔軟に対応可能。
- **運用面のメリット**: 「マップ上の座標ポイント(A-1地点など)」を固定したまま、そこに配置する「棚バーコード」を後から紐付け直す運用が可能。

MVPの対象は単一のデモ店舗のみだが(`docs/仕様書.md`)、将来のマルチテナント化を見据えて全テーブルに `store_id` を持たせている。

## 2. エンティティリレーション図

```
[auth.users] (Supabase標準認証)
     │
     ▼
 [profiles] (管理者。id = auth.users.id, store_idで担当店舗と紐付け)
     │
     ▼
  [stores] (店舗)
   │     │
   │     └──────────────┐
   ▼                    ▼
[shelf_locations]  [shelves] (棚) ◄───(1:1)─── [products] (商品)
 (Unity座標) ▲          │
             └──────────┘ (location_idで紐付け)
```

### 3.2 shelf_locations(棚位置テーブル)

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | UUID | PK, DEFAULT `gen_random_uuid()` | |
| store_id | UUID | NOT NULL, FK -> `stores.id` | |
| location_code | TEXT | NOT NULL | 位置識別コード。Unity側の棚オブジェクト名と合わせ `Shelf_` + 2桁ゼロ埋め連番の形式(例: `Shelf_08`)で統一する。DBの値をそのままUnityへのAPIレスポンスに使う(変換しない) |
| unity_position_x/y/z | FLOAT8 | NOT NULL, DEFAULT `0.0` | Unity座標 |
| created_at | TIMESTAMPTZ | DEFAULT `now()` | |

制約: `UNIQUE(store_id, location_code)` — 同一店舗内での位置コード重複登録を防ぐ。

**Unity連携の命名規則(確認済み)**: Unity側は`Shelf_08`/`08`/`8`のいずれの形式も受け取れるが、MVPでは`Shelf_08`形式に統一する。Unityへ棚IDを渡す際は`shelves.id`(UUID)や`shelves.barcode`(商品登録用の物理バーコード)ではなく、この`location_code`を使う。

**Unity側の棚カテゴリ対応表(確認済み)**: Unity側の3D店内マップには以下の8棚が固定で存在し、
これ以外のカテゴリ(「調味料」「日用品」等)の棚は存在しない。商品を登録する際は、
必ずこの8カテゴリのいずれかに該当する`location_code`へ紐付けること(`products.category`の
表記もUnity側のラベルと一致させる)。

| location_code | Unity側のラベル |
|---|---|
| Shelf_01 | 青果 |
| Shelf_02 | 精肉 |
| Shelf_03 | 鮮魚 |
| Shelf_04 | 惣菜 |
| Shelf_05 | 加工食品(調味料・レトルト・インスタント食品・缶詰等はここに含める) |
| Shelf_06 | 冷凍食品 |
| Shelf_07 | 飲料 |
| Shelf_08 | 乳製品 |

「日用品」等、上記に対応するUnity側の棚が存在しないカテゴリの商品は、無理に別の棚へ
紐付けず登録を保留する。

> **2026-09-06追記**: この対応表は3D側の見た目(ラベル)の話であり、8節で追加した
> `shelf_locations.category_id`(正式カテゴリDBとの紐付け)とは独立している。例えば
> `Shelf_05`は3D上「加工食品」と表示され続けるが、`category_id`は正式カテゴリの「衛生」
> (`CAT_05`)を指す。この不一致は本追記の時点では解消していない(8.10節参照)。

### 3.3 shelves(棚テーブル)

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | UUID | PK, DEFAULT `gen_random_uuid()` | |
| store_id | UUID | NOT NULL, FK -> `stores.id` | |
| location_id | UUID | FK -> `shelf_locations.id`, NULL可 | 紐づくUnity位置。未配置の棚も登録可能 |
| barcode | TEXT | NOT NULL, UNIQUE | 棚バーコード番号 |
| created_at | TIMESTAMPTZ | DEFAULT `now()` | |

**棚バーコードの採番規則(確認済み)**: EAN-13(13桁)形式で統一する。当初、デモデータの棚
バーコードはチェックデジット(13桁目)が未計算のただの連番だったため、実際に印刷して
EAN-13対応スキャナー(本アプリのバーコードスキャナー含む)で読み取ると無効なコードとして
弾かれる不具合があった。これを踏まえ、以下の規則で採番し直す。

| 桁位置 | 内容 | 値の範囲 |
|---|---|---|
| 1-3 | JAN日本国コード(既存踏襲) | `490` 固定 |
| 4 | 棚(什器)バーコードを表す固定値 | `9` 固定(商品バーコードは桁4が`1`のため衝突しない) |
| 5-6 | ゾーン番号(`location_code`の`Shelf_XX`の数字部分と一致) | `01`〜`08` |
| 7-8 | ゾーン内の棚枝番(何本目の物理棚か) | `01`〜`03`(増設時は`04`以降を追加可) |
| 9-12 | 予備(将来のマルチテナント化・増設用) | `0000` 固定 |
| 13 | チェックデジット | EAN-13標準アルゴリズムで算出 |

例: 青果ゾーン(`Shelf_01`)の1本目の棚 → `490` + `9` + `01` + `01` + `0000` + チェックデジット
= `4909010100006`

チェックデジットの計算式: 桁1〜12について、奇数桁(1,3,5,7,9,11桁目)の合計×1 と
偶数桁(2,4,6,8,10,12桁目)の合計×3 を足し、10で割った余りを10から引く(余りが0なら
チェックデジットも0)。新規に棚を追加する場合もこの規則・計算式に従うこと。
商品(products)バーコードは今回のスコープ外で、従来通りの採番のまま。

### 3.4 products(商品テーブル)

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | UUID | PK, DEFAULT `gen_random_uuid()` | |
| store_id | UUID | NOT NULL, FK -> `stores.id` | |
| shelf_id | UUID | UNIQUE, FK -> `shelves.id` | 1棚1商品を保証 |
| barcode | TEXT | NOT NULL, UNIQUE | 商品バーコード番号 |
| name | TEXT | NOT NULL | 商品名 |
| category | TEXT | | 属性・大まかなカテゴリ |
| description | TEXT | | AI検索用の詳細説明 |
| created_at | TIMESTAMPTZ | DEFAULT `now()` | |

**運用ルール(確認済み)**: 1棚につき商品は1件のみ。商品削除フローの「その棚に登録済みの商品一覧」は0件または1件のリスト表示として扱う。

> **2026-09-06追記**: `category_id UUID NULL REFERENCES categories(id)`を追加した(8節参照)。
> `category`(この表の通り自由記述、Unity側ゾーン名)は互換性のため残し、削除・書き換えは
> していない。新規登録商品は`category`(正式カテゴリの日本語名)と`category_id`の両方を保存する。
> 既存商品の`category_id`は無条件では設定せず`NULL`のまま。

### 3.5 profiles(管理者プロフィールテーブル)

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | UUID | PK, FK -> `auth.users.id` | |
| store_id | UUID | FK -> `stores.id` | 担当店舗ID |
| updated_at | TIMESTAMPTZ | DEFAULT `now()` | |

**認証方式(確認済み)**: 管理者ログインはSupabase Auth標準のメールアドレス+パスワードを使用する(`docs/仕様書.md` の「店舗ID(ユーザー名)」という記述は「メールアドレス」に読み替える)。

### 3.6 barcode_lookup_cache(バーコード検索キャッシュテーブル)

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| barcode | TEXT | PK | 商品バーコード番号 |
| name | TEXT | NOT NULL | 確定済みの商品名 |
| description | TEXT | | 確定済みの商品説明 |
| updated_at | TIMESTAMPTZ | DEFAULT `now()` | |

**運用ルール(確認済み)**: 商品登録・更新(`/api/admin/product-registration`)が成功するたびに、そのバーコードの
最終的な`name`/`description`をこのテーブルにupsertする。商品バーコードスキャン時(`/api/admin/product-lookup`)は
Yahoo!ショッピング商品検索APIより先にこのテーブルを参照し、ヒットすればそちらを優先する。
`products`とは独立したテーブルのため、商品が棚から削除されてもキャッシュは残り続ける
(=一度スタッフが手直しした名前・説明は、同じバーコードを再度登録する際に毎回使い回せる)。
RLSは有効化しているがポリシーは作成しておらず、service roleキー経由のサーバーAPIからのみ
読み書きする(他の管理者向けテーブルと同じ方針)。

### 3.7 product_translations(商品翻訳キャッシュテーブル)

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| product_id | UUID | PK(localeと複合), FK -> `products.id` ON DELETE CASCADE | |
| locale | TEXT | PK(product_idと複合) | `en`/`zh`/`ko`(日本語`ja`は翻訳不要のため保存しない) |
| description | TEXT | NOT NULL | 翻訳済み商品説明 |
| translated_at | TIMESTAMPTZ | DEFAULT `now()` | |

**運用ルール(確認済み)**: 消費者向け画面の多言語対応(日本語・英語・中国語簡体・韓国語)のうち、
商品説明文の翻訳結果をキャッシュする。検索・商品案内時にlocaleが日本語以外であれば
まずこのテーブルを参照し、無ければGoogle Cloud Translation APIを呼んで翻訳・保存する。
**商品名は翻訳しない**(店頭の実際の商品名と一致させるため、常に元の日本語のまま表示する。
当初はnameカラムも用意していたが、2026-09-05にユーザーの指示で「商品名は翻訳しない」方針に
変更したためカラムごと削除した)。
`barcode_lookup_cache`とは異なり`products`のライフサイクルに従属させる(商品削除時に
`ON DELETE CASCADE`で翻訳も削除してよい)。カテゴリ(8種の固定ゾーン名)は種類が少なく
固定的なため、このテーブルではなくアプリ側の静的対応表(`src/lib/i18n/categoryLabels.ts`)で
変換する(翻訳APIを呼ばない)。RLSは有効化しているがポリシーは作成しておらず、
service roleキー経由のサーバーAPIからのみ読み書きする。

## 4. DDL

```sql
-- 1. 店舗テーブル (stores)
CREATE TABLE stores (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  description TEXT,
  entry_qr_code TEXT NOT NULL UNIQUE,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- 2. 棚位置テーブル (shelf_locations)
CREATE TABLE shelf_locations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  store_id UUID NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  location_code TEXT NOT NULL,
  unity_position_x DOUBLE PRECISION NOT NULL DEFAULT 0.0,
  unity_position_y DOUBLE PRECISION NOT NULL DEFAULT 0.0,
  unity_position_z DOUBLE PRECISION NOT NULL DEFAULT 0.0,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL,
  UNIQUE (store_id, location_code)
);

-- 3. 棚テーブル (shelves)
CREATE TABLE shelves (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  store_id UUID NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  location_id UUID REFERENCES shelf_locations(id) ON DELETE SET NULL,
  barcode TEXT NOT NULL UNIQUE,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- 4. 商品テーブル (products)
CREATE TABLE products (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  store_id UUID NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  shelf_id UUID UNIQUE REFERENCES shelves(id) ON DELETE SET NULL,
  barcode TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  category TEXT,
  description TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- 5. 管理者プロフィールテーブル (profiles)
CREATE TABLE profiles (
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  store_id UUID REFERENCES stores(id) ON DELETE SET NULL,
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- 6. バーコード検索キャッシュテーブル (barcode_lookup_cache)
CREATE TABLE barcode_lookup_cache (
  barcode TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  description TEXT,
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- 7. 商品翻訳キャッシュテーブル (product_translations)
CREATE TABLE product_translations (
  product_id UUID NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  locale TEXT NOT NULL,
  description TEXT NOT NULL,
  translated_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL,
  PRIMARY KEY (product_id, locale)
);

-- パフォーマンス最適化 (インデックス)
CREATE INDEX idx_products_search ON products(name, category);
CREATE INDEX idx_products_store ON products(store_id);
CREATE INDEX idx_shelves_store ON shelves(store_id);
CREATE INDEX idx_shelf_locations_store ON shelf_locations(store_id);
CREATE INDEX idx_products_barcode ON products(barcode);
CREATE INDEX idx_shelves_barcode ON shelves(barcode);
CREATE INDEX idx_profiles_store_id ON profiles(store_id);
CREATE INDEX idx_shelves_location_id ON shelves(location_id);
CREATE INDEX idx_product_translations_product ON product_translations(product_id);
```

## 5. RLS(Row Level Security)ポリシー

管理者画面はSupabase Authで認証したユーザーが自店舗のデータのみ読み書きできるようにする。消費者向けの商品検索・ナビゲーションAPI(Next.js API route経由でClaude Agent SDKが呼び出す)は **`service_role` キーをサーバーサイドのみで使用してRLSをバイパスする**前提とし、`anon` キーをクライアントに渡して直接テーブルを読ませることはしない。

```sql
ALTER TABLE stores ENABLE ROW LEVEL SECURITY;
ALTER TABLE shelf_locations ENABLE ROW LEVEL SECURITY;
ALTER TABLE shelves ENABLE ROW LEVEL SECURITY;
ALTER TABLE products ENABLE ROW LEVEL SECURITY;
ALTER TABLE profiles ENABLE ROW LEVEL SECURITY;
ALTER TABLE barcode_lookup_cache ENABLE ROW LEVEL SECURITY;
-- barcode_lookup_cacheにはポリシーを意図的に作成しない(service roleキー経由のみで読み書き)
ALTER TABLE product_translations ENABLE ROW LEVEL SECURITY;
-- product_translationsにもポリシーを意図的に作成しない(service roleキー経由のみで読み書き)

-- profiles: 本人の行のみ参照・更新可
-- auth.uid()は行ごとの再評価を避けるため (select auth.uid()) の形で呼び出す
CREATE POLICY profiles_select_own ON profiles
  FOR SELECT USING (id = (select auth.uid()));

CREATE POLICY profiles_update_own ON profiles
  FOR UPDATE USING (id = (select auth.uid()));

-- stores / shelf_locations / shelves / products:
-- 認証済みユーザーは自分のprofiles.store_idと一致するstore_idの行のみ操作可
CREATE POLICY stores_admin_all ON stores
  FOR ALL USING (
    id IN (SELECT store_id FROM profiles WHERE profiles.id = (select auth.uid()))
  );

CREATE POLICY shelf_locations_admin_all ON shelf_locations
  FOR ALL USING (
    store_id IN (SELECT store_id FROM profiles WHERE profiles.id = (select auth.uid()))
  );

CREATE POLICY shelves_admin_all ON shelves
  FOR ALL USING (
    store_id IN (SELECT store_id FROM profiles WHERE profiles.id = (select auth.uid()))
  );

CREATE POLICY products_admin_all ON products
  FOR ALL USING (
    store_id IN (SELECT store_id FROM profiles WHERE profiles.id = (select auth.uid()))
  );
```

## 7. 適用状況

上記DDL・RLSポリシーはSupabase MCP経由で実際のプロジェクトに適用済み(テーブル作成→RLS設定→
Advisor指摘への対応〈未インデックスFKの追加、`auth.uid()`の`(select auth.uid())`化〉の順に3回に分けて適用)。
リポジトリには`supabase/migrations/20260830142800_init_schema.sql`として、適用後の最終状態を
1ファイルにまとめて保存している(共有・Supabase CLIでの再現用)。本ドキュメントのDDL・RLSも
その最新内容に更新済み。

なお、Supabaseプロジェクト側の適用履歴(マイグレーション管理テーブル)には3回分の記録が残っており、
このリポジトリの1ファイルとは1:1に対応しない。CLIで`supabase db push`等を行う場合は、
この点に注意すること。

その後、`barcode_lookup_cache`テーブルをSupabase MCP経由で追加適用し(バージョン`20260902142329`)、
`supabase/migrations/20260902142329_barcode_lookup_cache.sql`として保存している。

さらにその後、消費者向け画面の多言語対応にあわせて`product_translations`テーブルを追加適用し
(バージョン`20260905024739`)、`supabase/migrations/20260905024739_product_translations.sql`
として保存している。

TypeScript向けの型定義は`src/lib/supabase/database.types.ts`にスキーマから生成したものを保存している。
画面実装用のデモデータ(店舗1件・Unity 8棚分の棚位置、各棚位置に物理棚3件・商品3件ずつ、
計24棚24商品)を`supabase/seed.sql`として用意し、Supabaseプロジェクトにも投入済み。
棚(shelves)バーコードは3.3節の採番規則(EAN-13、チェックデジット計算済み)で
振り直し済み(旧: ただの連番 → 新: 上記規則に基づく値)。
管理者アカウント(`profiles`)はSupabase Authのサインアップを経由する必要があるため、
シードデータには含めていない(各自サインアップして手動で紐付ける)。

## 8. カテゴリDB・棚卸しデータ(2026-09-06追記)

本節は`supabase/migrations/20260906090000_categories_and_inventory.sql`の内容の説明。
**2026-09-06時点でリモートSupabaseへは未適用**(ローカルのmigrationファイルのみ存在し、
1〜7節が説明する既存スキーマ・DDLは変更していない)。3D(Unity/`store-3d/`)関連のコードは
本追記の対象外で変更していない。

### 8.1 背景・方針

- 目的は大きく2つ: (1) 検索語→カテゴリ→商品の紐付けによる検索精度向上、(2) 棚卸し
  (実地在庫確認)CSVの取込
- 正式カテゴリは8種(食品/文具/電気/化粧/衛生/トラベル/掃除/キッチン)。8.5節の通り
  `Shelf_01`〜`Shelf_08`と1:1対応させる
- 既存`products.category`(自由記述、3.2節のUnity側ゾーン名: 青果/精肉/鮮魚/惣菜/加工食品/
  冷凍食品/飲料/乳製品)は互換性のため削除・一括変更しない。新規登録商品は正式8カテゴリから
  選ばせ、`products.category`(選んだカテゴリの日本語名、互換用)と`products.category_id`
  (正式、`categories.id`)の両方を保存する。既存商品の`category_id`は無条件では設定せず
  `NULL`のまま維持する

### 8.2 categories(カテゴリマスタ)

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | UUID | PK, DEFAULT `gen_random_uuid()` | |
| code | TEXT | NOT NULL, UNIQUE, 空文字不可 | `CAT_01`〜`CAT_08` |
| name | TEXT | NOT NULL, 空文字不可 | カテゴリ表示名(例: 「衛生」) |
| display_order | INTEGER | NOT NULL, 0以上 | 一覧表示順 |
| is_active | BOOLEAN | NOT NULL, DEFAULT true | falseのものは検索・選択肢から除外 |
| created_at / updated_at | TIMESTAMPTZ | DEFAULT `now()` | |

RLS: 有効化のみでポリシーは作成しない(`barcode_lookup_cache`と同じ方針。service roleキー
経由のサーバーコードのみが読み書きする)。管理者用の変更API(作成・編集・削除)は今回作らない。

### 8.3 category_keywords(検索キーワード)

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | UUID | PK | |
| category_id | UUID | NOT NULL, FK -> `categories.id` ON DELETE CASCADE | |
| keyword | TEXT | NOT NULL, 空文字不可 | 表示・記録用の元表記 |
| normalized_keyword | TEXT | NOT NULL, 空文字不可 | `src/lib/category/normalize.ts`の`normalizeCategoryText()`と同じ変換をかけた値 |
| priority | INTEGER | NOT NULL, DEFAULT 0, 0以上 | 現状は未使用(将来の並び替え用に予約) |
| created_at / updated_at | TIMESTAMPTZ | DEFAULT `now()` | |

制約: `UNIQUE(category_id, normalized_keyword)`。**`normalized_keyword`単独のUNIQUE制約は
意図的に作らない** — 同じキーワードが複数カテゴリへ登録できる構造にするため(例:
「スポンジ」→ 掃除・キッチンの両方)。RLSはcategoriesと同じ方針(ポリシー無し)。

### 8.4 products.category_id / shelf_locations.category_id

- `products.category_id UUID NULL REFERENCES categories(id)` — 8.1節の通り、既存`category`
  列とは独立して追加。インデックス`idx_products_category_id`あり
- `shelf_locations.category_id UUID NULL REFERENCES categories(id)` — `Shelf_01`〜`08`という
  売り場ゾーンが正式カテゴリのどれに当たるかを表す(3D側のゾーン名/ラベルとは独立、8.5節参照)。
  インデックス`idx_shelf_locations_category_id`あり

### 8.6 inventory_counts(棚卸しデータ)

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | UUID | PK | |
| store_id | UUID | NOT NULL, FK -> `stores.id` ON DELETE CASCADE | 認証済み管理者の`profiles.store_id`を正本として使う(CSVの`store_code`は照合のみに使い信用しない) |
| product_id | UUID | NULL, FK -> `products.id` ON DELETE SET NULL | CSVの`jan_code`から解決。未登録なら`NULL` |
| shelf_location_id | UUID | NULL, FK -> `shelf_locations.id` ON DELETE SET NULL | CSVの`shelf_code`から解決 |
| sku | TEXT | NOT NULL, 空文字不可 | 棚卸し側の管理番号(`products`のカラムではない。任意の文字列) |
| jan_code | TEXT | NULL | 商品バーコード。`products.barcode`との突き合わせに使う(任意列) |
| category_id | UUID | NULL, FK -> `categories.id` ON DELETE SET NULL | CSVの`category_code`から解決 |
| book_stock | INTEGER | NULL, 0以上 | 帳簿在庫(任意) |
| actual_stock | INTEGER | NOT NULL, 0以上 | 実地在庫 |
| unit | TEXT | NULL | 単位(任意) |
| cost_price / selling_price | NUMERIC | NULL, 0以上 | 原価・売価(任意) |
| counted_at | TIMESTAMPTZ | NOT NULL | 棚卸し日時。CSVは`YYYY-MM-DD`または`YYYY-MM-DD HH:mm[:ss]`のみ許可し、**UTCとして解釈する**(詳細はCSV仕様書) |
| created_at / updated_at | TIMESTAMPTZ | DEFAULT `now()` | |

制約: `UNIQUE(store_id, sku, counted_at)` — 同一店舗・同一skuでも別日時の棚卸しは許可しつつ、
同じCSVの誤った二重取込を防ぐ。RLSは`products`等と同じ「担当店舗のみ」パターン
(`inventory_counts_admin_all`)を付けているが、実際の読み書きは管理者APIがService Role Client
経由で行うため、通常はこのポリシーを経由しない(多層防御・将来のセッション付きクライアント
利用に備えたもの)。

`product_id`/`shelf_location_id`/`category_id`はすべてNULL許容。商品未登録のSKUも
(誤案内を避けるため自動で`products`へ登録することはせず)`product_id`を`NULL`にしたまま
棚卸し記録として保存できるようにするための設計。

### 8.7 検索フロー(カテゴリ検索とOpenCLIPの統合)

既存のOpenCLIP検索(`src/lib/aiSearch/`)は削除・置換していない。`src/app/api/search/route.ts`で、
既存のOpenCLIP/フォールバック検索とは別に以下を実行し、結果を統合する。

```
検索語
  ↓ normalizeCategoryText()で正規化(前後空白・連続空白・英字大小・NFKCによる安全な範囲の全半角差を吸収)
  ↓ category_keywordsから完全一致 or 文文中一致(短すぎるキーワードは部分一致対象外)する
     キーワードを探す(src/lib/category/categoryMatch.ts)
  ↓ 一致した(複数もありうる)カテゴリのidを求める
  ↓ products.category_idが一致する商品を検索候補にする
既存のOpenCLIP検索(searchProductsWithClip)/失敗時のfallbackSearchは従来通り並行して実行
  ↓
両方の結果をproduct_idで重複除去して統合(src/lib/category/mergeSearchMatches.ts。
カテゴリ側を先に統合することで、一致した場合はカテゴリ側の一致理由を残す)
  ↓
既存のレスポンス形式(SearchResultItem[])で返す
```

カテゴリDBへのアクセス(`fetchCategoryKeywordIndex`)は内部で例外を捕捉し、失敗時は空配列を
返す。カテゴリDBが未適用・障害中でも検索全体(OpenCLIP・フォールバック検索)は継続する。

### 8.8 商品→棚番の取得経路(変更なし)

3D案内の最終的な棚特定経路は本追記でも変更していない。

```
商品選択 → /navigate/[productId] → getProductWithShelfLocation(productId)
  → products.shelf_id → shelves.location_id → shelf_locations.location_code
  → Shelf_01〜Shelf_08 → 既存3D案内
```

カテゴリ(`category_id`)を3D目的地の決定に直接使う経路は追加していない。商品の
`category_id`と、その商品が置かれた棚(`shelf_locations.category_id`)が異なる場合も、
棚IDや商品カテゴリを自動修正せず、検索・案内自体は止めない(整合性の警告に留める)。

### 8.9 棚卸しCSV(概要)

管理者専用(`requireAdminSession()`必須)。列仕様・検証内容・サンプルの詳細は
[`docs/棚卸しCSV仕様.md`](./棚卸しCSV仕様.md)を参照。要点のみ:

- プレビュー(`/api/admin/inventory/preview`)と確定(`/api/admin/inventory/import`)を分離し、
  どちらもサーバー側で同じ検証関数(`src/lib/inventory/validateInventoryCsv.ts`)を実行する
  (クライアント側の検証だけを信用しない)
- 商品未登録のSKU(CSVの`jan_code`が空、または`products.barcode`と一致しない)は
  自動登録しない。「要確認」行として保存はする(`product_id`は`NULL`)が、実際の商品登録は
  別途`/admin/products/new`で行う
- 確定APIは1件でも検証エラー行があれば何も保存しない。保存は複数行をまとめた1回の
  `insert`で行い、Postgresの単一SQL文としての原子性により一部の行だけ保存される状態を防ぐ
  (追加のRPC・トランザクション制御はこのスコープでは導入していない)
