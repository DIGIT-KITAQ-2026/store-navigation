# /merge-folder — 個人の作業フォルダを安全に取り込む

チームメンバーが `main` を共有しないまま個人のPC上で進めてしまった作業フォルダを、
このリポジトリに安全に取り込み、通常の「ブランチ+PR」フローに乗せ直すためのスキル。

対象フォルダは git 管理されている場合とされていない場合が両方あり得る。どちらの場合も
**このリポジトリと共有コミット履歴を持たない**ものとして扱い、コミット単位のマージではなく
**ファイル単位の差分比較**で扱う。

## Step 1 — 入力を確認する

`$ARGUMENTS` から次を読み取る。

- 取り込み対象フォルダの絶対パス(必須。無ければユーザーに聞く)
- 作業ブランチ名や担当者名・作業内容の概要(任意。無ければ対話で確認し、
  `CONTRIBUTING.md` の命名規則に沿ったブランチ名を一緒に決める。例: `feature/tanaka-search-ui`)

対象パスが存在し、ディレクトリであることを確認する。

## Step 2 — リポジトリの状態を確認する

- `git status` でこのリポジトリに未コミットの変更が無いか確認する。何かあればユーザーに提示し、
  先にコミット/stashするかどうか確認してから進める(黙って上書き・破棄しない)
- `git fetch` した上で `main`(または現在のデフォルトブランチ)を最新化する

## Step 3 — 作業ブランチを作成する

最新の `main` から、Step 1 で決めたブランチ名で新しいブランチを作成する。

```
git checkout main
git pull
git checkout -b <branch-name>
```

## Step 4 — 対象フォルダを解析する

- 対象フォルダに `.git` があるかどうかを確認する(あれば「gitリポジトリとして作業していたケース」、
  無ければ「ただのフォルダとして作業していたケース」として扱うが、比較方法は共通)
- `node_modules`, `.next`, `.git`, ビルド成果物などは比較対象から除外する
- 対象フォルダとこのリポジトリ(作業ブランチ)を比較し、次の3種類に分類する
  - リポジトリに無く、対象フォルダにのみ存在するファイル(新規)
  - 両方に存在し、内容が異なるファイル(変更)
  - リポジトリにあり、対象フォルダに無いファイル(削除候補。これは基本的に触らない — 対象フォルダには
    存在しないファイルの多くは単に「そのメンバーが触っていないだけ」であり、削除して良いとは限らないため)

## Step 5 — 1件ずつユーザーに確認する

新規ファイル・変更ファイルのそれぞれについて、

1. ファイルパスと概要(新規 or 変更)を示す
2. 変更ファイルは diff を表示する
3. 次の選択肢をユーザーに確認する
   - 取り込む(対象フォルダの内容をこのリポジトリに反映)
   - リポジトリ側を残す(取り込まない)
   - 保留(あとで手動で見る)

**絶対に確認なしで上書き・削除しない。** 一括で「全部取り込む」と明示的に指示された場合のみ、
確認をまとめて1回にしてよい。

ファイル数が多い場合は、似た種類のファイル(例: 同じディレクトリ配下)をまとめて確認してもよいが、
実際の反映前には必ず対象ファイル一覧を最終確認する。

## Step 6 — 反映してコミットする

承認された変更のみを作業ブランチのワーキングツリーに適用し、`git add` した上で、
取り込み元フォルダのパスと(分かれば)担当者名を含むコミットメッセージでコミットする。

## Step 7 — 結果を報告する

以下をまとめてユーザーに報告する。

- 作成した作業ブランチ名
- 取り込んだファイル一覧 / 見送った(反映しなかった)ファイル一覧
- 次にやること: `git push -u origin <branch-name>` してPRを作成すること

**push・PR作成はここでは自動実行しない。** ユーザーが望む場合のみ、確認した上で実行する。
